# LM-BE

Бекенд **LioMebli** — Spring Boot, публічний API каталогу й адмін-панель.

Частина робочої області [`LM-WORKSPACE`](https://github.com/LioMebli/LM-WORKSPACE).
Цей репозиторій має лежати всередині її теки — від цього залежать посилання
`@../../GLOBAL_DESCRIPTION_LM_PROJECT.md` у файлах контексту.

---

## Передумови

| Що | Версія | Навіщо |
|---|---|---|
| **JDK** | **25** (LTS, Temurin) | `pom.xml` збирається під 25; на 21 не скомпілюється |
| **Docker Desktop** | будь-яка актуальна | база, а також інтеграційні тести через Testcontainers |
| Maven | **не потрібен** | у репозиторії є обгортка `mvnw` |

Перевірити перед стартом:

```powershell
java -version      # має бути 25
docker info        # має відповісти, а не впасти
```

## Запуск — щоденний режим

```powershell
cd LM-BE
.\mvnw.cmd spring-boot:run "-Dspring-boot.run.profiles=local"
```

На Linux або macOS — `./mvnw spring-boot:run -Dspring-boot.run.profiles=local`.

**Дві команди, не три — і це не помилка.** Модуль `spring-boot-docker-compose`
піднімає `compose.yaml` сам під час старту застосунка й підставляє параметри
підключення до бази. Окремий `docker compose up -d` не потрібен: критерій «без
ручних дій» виконується буквально.

Він знадобиться лише тоді, коли базу треба мати піднятою **без** застосунка —
підключити SQL-клієнт, подивитися дані:

```powershell
docker compose up -d
```

Із IDE — те саме: запустити `LmBeApplication` з активним профілем `local` і
робочою текою `LM-BE`. Робоча тека важлива: саме поруч із нею шукається
`compose.yaml`.

> Щоденний цикл свідомо не контейнеризується. На Windows відстеження змін через
> bind mount ламає гаряче перезавантаження, тож бекенд працює з IDE, а в
> контейнерах живе лише база. Режим паритету — у README робочої області.

## Куди дивитися

| Адреса | Що |
|---|---|
| `http://localhost:8080` | API |
| `http://localhost:8080/actuator/health` | стан застосунка **і** бази |
| `localhost:5432` | PostgreSQL 18, база `appdb`, користувач `lmuser`, пароль `password` |

Пароль тут не секрет: він живе лише в локальному `compose.yaml` і в проді не
використовується. Продові облікові дані беруться з SSM Parameter Store.

Здоровий стан — це `{"status":"UP"}`, у якому серед компонентів є `db`. Якщо
`status` `UP`, а бази серед компонентів немає — застосунок піднявся без неї, і
перший же запит до каталогу впаде.

## Тести

```powershell
.\mvnw.cmd verify
```

Інтеграційні тести піднімають **справжню PostgreSQL** через Testcontainers — H2
не використовується свідомо, бо він поводиться інакше саме там, де каталог
навантажує базу найбільше. Отже: **без запущеного Docker тести не проходять**, і
повідомлення про помилку при цьому виглядає непов'язаним із Docker. Перевіряйте
це першим.

## Коли не працює

**Порт 8080 зайнятий.** Найчастіше через те, що паралельно піднятий режим
паритету. Подивитися й вимкнути:

```powershell
netstat -ano | Select-String ":8080"
docker compose -f ..\compose.full.yaml down
```

**Docker не запущений.** Симптом плаваючий: або `spring-boot-docker-compose` не
підніме базу і застосунок впаде на підключенні, або Testcontainers впаде з
довгим стеком про транспорт. Запустіть Docker Desktop і дочекайтеся, поки
`docker info` відповідає.

**База не піднялася.** Подивитися, що каже контейнер:

```powershell
docker compose logs postgres
```

Найчастіша причина — попередній том лишився від іншої версії PostgreSQL. Скинути
**разом із даними**:

```powershell
docker compose down -v
```

**`more than one row returned by a subquery` при старті — один раз після LM-61.**
Той самий скид тому лікує і це. Наповнення каталогу переїхало з
`seed/seed-local.yaml` у `seed/seed-catalog.yaml`, а Liquibase упізнає ченджсет за
трійкою `id` + `author` + **імʼя файлу** — тож у томі, де старий уже застосований,
новий виглядає незастосованим і вставляє категорії вдруге. Далі кожна вставка
товару шукає свою категорію підзапитом і знаходить дві.

Скидати том тут безпечно: локальна база не містить нічого, чого не відтворює
наповнення. **Після [LM-2](https://liomebli.atlassian.net/browse/LM-2) це вже не
так** — тоді таке перейменування коштуватиме дублікатів у справжніх даних, і
правильний хід буде інший: новий ченджсет, що заміщає старий.

**Помилка CORS у браузері.** Приходить із боку фронтенду, лагодиться тут.
Публічні читання під `/api/v1/**` відкриті для будь-якого джерела, адмінські
шляхи — лише для списку в `lm.cors.admin-origins` (`application-local.yaml`,
за замовчуванням `http://localhost:4200`). Якщо фронтенд запущений на іншому
порту, додайте його туди. Проксі між фронтендом і API немає навмисно: у проді
вони на різних доменах, і краще ловити це локально.

**Схема бази не збігається з сутностями.** Застосунок падає на старті —
`ddl-auto: validate` не створює таблиці, а лише перевіряє. Схему створює
Liquibase, і це правильна поведінка: мовчазне доліплювання стовпців у проді
гірше за падіння локально.
